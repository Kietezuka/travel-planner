# Travel Planner

[English](README.md) · **日本語**

「**どこで(where)**」と「**いつ(when)**」の分断を解消する、フルスタックの旅行計画Webアプリ。
行きたい場所のリストを、スケジュールと地図を1画面に並べて表示することで、具体的な日ごとの旅程へと落とし込みます。
それによって、ユーザーは旅行先につく前に実際の行きたい場所の距離感をイメージすることができます。

学士論文の制作物として、Human-Computer Interaction(HCI)、UIデザイン、レスポンシブWebデザインの理論を実際のアプリケーションに適用しました。

## 制作の背景

旅行の計画は、たいてい複数のアプリを行き来することになります。
Googleマップに保存した場所、カレンダーの日程、メモアプリなど。
行きたい場所を保存すればするほど、それを実際の日程に当てはめるのが難しくなります。
このアプリは地図とスケジュールを1つの計画画面に統合し、「どこ」にあるかを見ながら「いつ」行くかを決められるようにします。

## 機能

- **旅行の作成**： 行き先(OpenStreetMap オートコンプリート)と日付範囲を選択。両方が有効になるまで「Make Plan」ボタンは無効のままで、情報が欠けた状態で計画を始められないようにしています。
- **週間スケジュール表**： 旅行日数から列を自動生成。アクティビティは30分グリッドでサイズが決まるドラッグ可能なセルで、カテゴリごとに色分け。宿泊はチェックイン〜チェックアウト日をまたぐバーとして表示されます。
- **ドラッグ&ドロップによる並べ替え + Undo**： セルをドラッグするとデータベースが非同期で更新されます。他のアクティビティと重なるドロップは拒否され、説明とともに元の位置へ戻ります。すべての編集はトーストから取り消せます。
- **デイビュー**： その日のアクティビティを開始時刻順に並べ、Leaflet 地図と横に並べて表示。住所を持つアクティビティには番号付きのピンが立ち、カードにホバーすると対応するピンがハイライトされ、スケジュールと地図が連動します。日ごとのメモはフォーカスを外すと自動保存されます。
- **ゲストモード**： アカウントなしで旅程を丸ごと作成可能(localStorage に保存し、トレードオフを説明する常時バナーを表示)。サインアップ時にゲストの計画は新しいアカウントへ取り込まれるため、作業が失われません。
- **アカウント管理**： プロフィール編集、要件チェックリスト付きのパスワード変更、そして意図的な手間をかけたアカウント削除(折りたたまれた「danger」セクション + パスワード再入力 + 確認ダイアログ)。
- **クライアント・サーバー両方でのバリデーション**： 重複や時間範囲のルールはクライアントで検証し、書き込み前にサーバーでも再チェック。クライアント側のチェックが回避されてもスケジュールの整合性が保たれます。
- **常にステータスを可視化**： ボタンのローディング状態、オフラインバナー(「変更を保存できません」/「オンラインに復帰しました」)、保存中インジケーター、次の操作が明確な空状態。

## デザイン・実装のこだわり

### Material Design 3 のデザイントークン

ビジュアル言語全体を、小さな MD3 デザインシステムとして CSS カスタムプロパティで実装しています([tokens.css](src/app/styles/tokens.css))。各コンポーネントは生の値ではなく常にトークンを参照します。

- **カラーロール**： ポジティブな操作には `--md-primary`(インクブルー)、破壊的な操作には `--md-error`(レッド)、二次的な操作にはトーナルな `--md-secondary-container`、そして surface / on-surface のペア。これらをセマンティックエイリアス(`--color-text`、`--color-bg-card` など)にマッピングし、コンポーネントをパレットから切り離しています。
- **タイプスケール**： Roboto を用い、MD3 のロール(headline / title / body)を「サイズ + 行高 + 字間」のトークン三点セットとして定義。
- **シェイプとエレベーション**： ピル型ボタン(`--shape-full`)、12dp のカード、28dp のモーダル、重い影の代わりに3段階の重ね影スケール。
- **ステートレイヤーとモーション**： MD3 の hover/focus/press 不透明度と標準のイージング・デュレーショントークン。すべてのアニメーションは `prefers-reduced-motion` を尊重します。
- **トークンに組み込んだアクセシビリティ**： 48dp の最小タッチターゲットトークン、`html { font-size: 62.5% }` と rem 単位によりブラウザのフォント設定に追従するレイアウト(WCAG 1.4.4)、高コントラストのフォーカスリング、キーボードユーザー向けのスキップリンク。

### HCI 理論を具体的なUIの判断へ

- **実行の淵 / 評価の淵(Norman)**：「有効になるまで無効」の主ボタンが制約として機能。SPA ルーティングと即座に更新される表ヘッダーが、リロードなしで操作結果を確認させます。
- **Nielsen のヒューリスティック**： すべてのモーダルはフォーカスをトラップし、Escape/Cancel で閉じ、未保存の変更を破棄する前に警告。破壊的操作には確認を要求し、トーストで Undo を提供(「ユーザーの制御と自由」)。
- **認知的負荷**： アクティビティは日ごとにチャンク化(ミラーの法則)し、詳細は段階的開示の背後に隠します。週間ビューではコンパクトなカード、デイビューではフルカード、それ以外はモーダルの1クリック先。
- **サムゾーンのエルゴノミクス**： モバイルでは主要な「Add activity」操作が右下のナチュラルゾーンのフローティングアクションボタンに変形し、片手で届く位置に配置されます。

### レスポンシブ戦略(デスクトップファースト)

計画はノートPCで、確認は旅先のスマホで。レイアウトはデスクトップを起点に設計し、そこから縮小して適応させています。

| ブレークポイント | デバイス | レイアウト |
|---|---|---|
| ≥ 1025px | デスクトップ | 2ペイン分割:スケジュール 40% / 地図 60% |
| 641–1024px | タブレット | 最小高さを持つ地図を上部に、スクロールするリストを下部に |
| ≤ 640px | モバイル | 単一カラムのスタック、主要操作は FAB |

旅行特有の課題には個別の解決策を用意しました。
週間表はスマホでも列を縦積みにせず、横スクロールできるコンテナで日ごとの構造を維持します。
また地図は固定高のブロック内に置き、下方向のスワイプが地図のパンに奪われず、ページ自体をスクロールできるようにしています。

### データモデル

一対多のリレーションで構成したリレーショナルスキーマ([schema.sql](schema.sql)):ユーザーが旅行を所有し、旅行がアクティビティ・日メモ・宿泊を所有します。外部キーは `ON DELETE CASCADE` を用いており、旅行を削除するとその配下がすべてきれいに削除され、孤立レコードが残りません。パスワードは bcrypt ハッシュとしてのみ保存します。

プロジェクトはローカルの SQLite ファイル(better-sqlite3)で始まり、デプロイ済みのマルチデバイス環境のために libSQL/Turso へ移行しました。スキーマはそのまま引き継げたため、当初のリレーショナル設計の妥当性が裏付けられました。

## セットアップ手順

### 前提条件

- Node.js 20+

### 手順

```bash
# 1. 依存関係のインストール
npm install

# 2. 環境変数の設定
cp .env.example .env
```

`.env` を編集:

```bash
# 生成コマンド: openssl rand -base64 32
NEXTAUTH_SECRET=<your-secret>
NEXTAUTH_URL=http://localhost:3000

# 任意 — ローカル開発では空のままで可(ローカルの SQLite ファイルにフォールバック)
TURSO_DATABASE_URL=
TURSO_AUTH_TOKEN=
```

```bash
# 3. データベーススキーマの作成(Turso 変数が空なら file:local.db を使用)
npm run db:migrate

# 4. 開発サーバーの起動
npm run dev
```

[http://localhost:3000](http://localhost:3000) を開きます。ゲストモードですぐに計画を始めるか、永続的なアカウントを作成できます。

### 本番で Turso を使う場合

```bash
turso db show <db> --url          # -> TURSO_DATABASE_URL
turso db tokens create <db>       # -> TURSO_AUTH_TOKEN
npm run db:migrate                # リモートDBに schema.sql を適用
```

### スクリプト

| コマンド | 説明 |
|---|---|
| `npm run dev` | 開発サーバーを起動 |
| `npm run build` | 本番ビルド |
| `npm start` | 本番ビルドを配信 |
| `npm test` | ユニットテスト(Vitest)— バリデーションと重複判定ロジック |
| `npm run lint` | ESLint |
| `npm run db:migrate` | 設定済みのデータベースに `schema.sql` を適用 |

## 制約と今後の展望

- ジオコーディングは公開の Nominatim エンドポイント(レート制限あり)に依存しており、本番運用には専用プロバイダーが必要です。
- オフライン編集は検知(バナー)するものの、まだバッファリングはしていません、 再接続時に同期する PWA モードが次のステップです。
- その他のアイデア:リアルタイム共同編集の旅程、おすすめの場所などの提供、予定地点間のルート最適化、ダークテーマ、多言語対応。
